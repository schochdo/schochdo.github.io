1. Modern Zero-Framework Tech Stack

Zero node runtimes, zero bundlers, and zero framework overhead in production

100% Vanilla

Built entirely in Vanilla JavaScript (ES6+), semantic HTML5, and Tailwind CSS. The platform deliberately avoids monolithic frameworks (React, Angular, Vue) and production bundlers (Webpack, Vite), eliminating dependency drift, breaking ecosystem updates, and bloat.

  • • DOM Execution: Native browser API
  • • Performance: 60 FPS WebGL & Canvas

Multi-Engine

  • MapLibre GL JS v4.7.1: WebGL 3D terrain elevation, USGS 3DEP topography, and 83 streamflow reaches.

2. Serverless Strategy & GitHub Actions (Why No 24/7 Server?)

Eliminating fragile sleeping containers and infrastructure overhead via static edge distribution

The 24/7 Server Dilemma vs. Static Edge Architecture

Traditional hydrologic portals run 24/7 server processes (Flask, Django, Node.js) on virtual machines or containers (e.g. AWS EC2, Heroku). In practice, this architectural choice creates four severe engineering failure modes:

1. Cold-Start Latency & Sleeping Dynos: When traffic pauses, cloud containers spin down. The next visitor experiences 15–30 second cold starts while the operating system and Python environment boot.
2. Security Attack Surface: Exposing a live Python web server to the public internet requires continuous security patching, SSL certificate rotation, SSH hardening, and DDoS mitigation.
3. Hosting Costs & Downtime: A 24/7 dedicated server generates recurring monthly bills even when zero users are viewing data, and crashes immediately if background memory leaks occur.

The Decoupled Static Edge Solution

Instead of running a live server, this platform compiles all hydrologic records into versioned, static JSON contracts distributed via GitHub Pages. This provides:

1. Instant Sub-50ms Global Loading: Static assets are cached at Fastly CDN edge nodes across the world. Zero cold starts, zero backend query latency, and 100% uptime.
2. Twice-Daily Scheduled GitHub Action (06:00 & 18:00 UTC): An automated CI/CD workflow (.github/workflows/update_data.yml) triggers twice every day. It spins up an ephemeral Ubuntu runner, executes the Python ingestion scripts, queries USGS/USBR/CDSS APIs, refreshes the SQLite database, validates mass-balance invariants, updates the static JSON files, and commits the updates directly to GitHub, triggering instant zero-downtime redeployment.
3. Zero Operating Cost & Infinite Scaling: Because only static files are served, the dashboard can handle 10 simultaneous visitors or 100,000 visitors without incurring a dime in hosting expenses or slowing down.

3. The Relational SQLite Basin Database (colorado_river_basin.db)

Structured relational persistence bridging messy raw government feeds with lightweight client JSON contracts

The project utilizes an embedded relational SQLite database (data/colorado_river_basin.db). Flat files alone cannot enforce data types, maintain foreign key integrity across multiple federal agencies, or calculate multi-year rolling aggregates efficiently. SQLite delivers full ACID compliance, zero setup, and millisecond query execution within a single 2.5 MB portable file.

The 4 Static JSON Export Contracts

Python scripts compile SQL query views from SQLite into four decoupled, static JSON payloads placed in web/data/:

latest_metrics.json ~45 KB • Live flow rates, storage volumes, and flow health tiers for all 92 stations.
river_network.json ~120 KB • Topological DAG connecting 83 reaches with flow scaling weights.
station_hierarchy.json ~35 KB • Sentinel classifications, priority gaging tiers, and coordinates.
seasonal_regimes.json ~180 KB • 365-day hydrograph curves and 104-year Compact balance timelines.

4. Hybrid Real-Time Hydrology: How Live Data Works Without a 24/7 Server

Two-tier client-side fetch architecture ensuring live telemetry with zero-failure fallback

Tier 1: Client-Side Direct REST Queries (CORS-Enabled)

When a user visits the interactive map or facility ledger, the browser executes a direct client-side fetch (fetch() in web/app.js) against the official USGS NWIS REST API (waterservices.usgs.gov):

// Direct client-side browser query (No backend proxy required)
const url = `https://waterservices.usgs.gov/nwis/iv/?sites=${sites}&parameterCd=00060,00065&format=json`;
const response = await fetch(url);
const nwisJson = await response.json();

Because the USGS NWIS REST service officially supports Cross-Origin Resource Sharing (CORS), the user's web browser receives live 15-minute telemetry directly from government servers without routing through any intermediary backend server.

Tier 2: Graceful Static Fallback (Zero-Break Resilience)

What happens if the user is offline, the federal API has scheduled maintenance, or strict government rate-limiting blocks the client?

The Resilient Fallback Cascade:

In web/app.js, if the live USGS fetch encounters a network timeout, HTTP error, or CORS rejection, the app silently and seamlessly falls back to loading web/data/latest_metrics.json (the snapshot updated twice daily by GitHub Actions).

The user interface never crashes, displays zero broken error banners, and always provides a 100% operational hydrologic dataset.
