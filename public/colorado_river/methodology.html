1. Modern Zero-Framework Tech Stack

Zero node runtimes, zero bundlers, and zero framework overhead in production

Frontend Architecture

Built entirely in Vanilla JavaScript (ES6+), semantic HTML5, and Tailwind CSS. The platform deliberately avoids monolithic frameworks (React, Angular, Vue) and production bundlers (Webpack, Vite), eliminating dependency drift, breaking ecosystem updates, and bloat.

  • • Build Step: None (No bundler or npm runtime)
  • • DOM Execution: Native browser APIs
  • • Rendering: WebGL (MapLibre) & HTML5 Canvas

Visualization Engines

Each interface view uses a specialized rendering engine matched to its domain physics:

  • MapLibre GL JS v4.7.1: WebGL 3D terrain elevation, USGS 3DEP topography, and 83 streamflow reaches.
  • D3.js v7: Flow-proportional mass-balance Sankey network closing at exact 14.14 MAF/yr (2000–2024 USBR accounting).
  • Chart.js v4: Responsive 365-day hydrographs, seasonal heartbeats, and 103-year Compact timelines (Water Years 1922–2024).

Data Pipeline & Storage

Data extraction, geospatial network topology, and numerical aggregations are powered by standard scientific Python libraries (requests, sqlite3, pandas, scipy). All data resides in a local ACID-compliant relational SQLite database.

  • • Database: SQLite 3 (colorado_river_basin.db)
  • • Automation: Scheduled GitHub Actions
  • • Verification: Headless Chrome CDP tests

2. Serverless Strategy & GitHub Actions (Why No 24/7 Server?)

Eliminating fragile sleeping containers and infrastructure overhead via static edge distribution

The 24/7 Server Dilemma vs. Static Edge Architecture

Traditional hydrologic portals run 24/7 server processes (Flask, Django, Node.js) on virtual machines or containers (e.g. AWS EC2, Heroku). For a small research project, this introduces three common operational trade-offs:

1. Cold-Start Latency & Sleeping Dynos: When traffic pauses, cloud containers spin down. The next visitor experiences 15–30 second cold starts while the operating system and Python environment boot.
2. Security Attack Surface: Exposing a live Python web server to the public internet requires continuous security patching, SSL certificate rotation, SSH hardening, and DDoS mitigation.
3. Hosting Costs & Downtime: A 24/7 dedicated server generates recurring monthly bills even when zero users are viewing data, and crashes immediately if background memory leaks occur.

The Decoupled Static Edge Solution

Instead of running a live server, this platform compiles all hydrologic records into versioned, static JSON contracts distributed via GitHub Pages. This provides:

1. Fast Static CDN Delivery: Static assets are cached at CDN edge nodes with no cold starts or backend database query latency.
2. Scheduled GitHub Action (Every 6 Hours — 00:00, 06:00, 12:00, 18:00 UTC): An automated CI/CD workflow (.github/workflows/update_data.yml) runs four times daily. Each run executes the Python ingestion scripts against USGS, USBR, and CDWR APIs, refreshes the SQLite database and static snapshots (latest_metrics.json, replay_7d.json, replay_30d.json), and publishes updated files. The 7D (1-hour) and 30D (2-hour) Flow Replay matrices pull USGS's rolling 15-minute archive (period=P7D / P30D), so every hourly replay step reflects genuine USGS observations rather than action-run intervals.
3. Zero Hosting Cost & Simple Scaling: Because only static files are served, the site handles traffic spikes through CDN caching without recurring server bills.

4. Hybrid Real-Time Hydrology: How Live Data Works Without a 24/7 Server

Two-tier client-side fetch architecture pairing live USGS queries with a static snapshot fallback

Tier 1: Direct Browser-to-Agency Fetching (CORS-Enabled REST)

When a user visits the interactive map or facility ledger, the browser executes a direct client-side fetch (fetch() in web/app.js) against the official USGS NWIS REST API (waterservices.usgs.gov):

// Direct browser query to federal servers (No middleman proxy required)
const url = `https://waterservices.usgs.gov/nwis/iv/?sites=${sites}&parameterCd=00060,00065&format=json`;
const response = await fetch(url);
const nwisJson = await response.json();

Why CORS matters: By default, web browsers block web pages on one domain (such as GitHub Pages) from fetching data from a different domain (like usgs.gov) under the Cross-Origin Resource Sharing (CORS) security standard. Because USGS officially includes open CORS permission headers (Access-Control-Allow-Origin: *) on their REST responses, the user's browser can retrieve live 15-minute gage measurements directly from federal servers without needing a dedicated backend proxy.

Tier 2: Static Snapshot Fallback (API Outage Resilience)

What happens if the USGS NWIS API has scheduled maintenance, times out, or rate-limits requests while the site itself is still reachable (or when running a local clone without external API access)?

Static Snapshot Fallback:

In web/app.js, if the live USGS fetch encounters a network timeout, HTTP error, or browser connectivity issue, the app falls back to loading web/data/latest_metrics.json (the static snapshot refreshed every 6 hours by GitHub Actions). Monthly-published USGS stations (CAP 09426650, Morelos 09522000) display their exact last-published date, and discontinued stations (09424150) are explicitly marked discontinued rather than filled with placeholders.

This keeps the map and station ledger populated with recent basin data during upstream federal API outages, without requiring a backend proxy.
